# Vidu 真实有声对话验证

## 短句起播超时与错误状态修复（2026-10-25）

真实五轮复测先重现“我在。”短句无声取消，源 PCM 时长 1.04 秒、有声区间约 0.62 秒。
400 ms 首窗相关度约 0.68，整段短句约 0.40，但三个连续 100 ms 有声片段分别约
0.92 / 0.93 / 0.87。真实回传中的局部时序变化导致长窗失配，不能直接当作 RTC 断连。

新增连续短片段起播确认（每段门限仍为 0.8），支持由三个可靠锚点按完整剩余源时长、
余量、远端安静和实际输出时钟估算结束；不改变严格完整匹配进度，不把缺失内容声明为匹配。
故障短句曾用于 2 kHz f32le 小型夹具回归；对应对齐代码、夹具和测试已随方案撤回，
当前工作区不再包含它们。采样来自固定生成的测试回复，不含麦克风录音或凭据。

修复后同一 live 五轮真实测试通过：两轮普通短句、两轮额外短回复（“我在。”、“好的，请继续。”）
均 started/ended，一轮长回复播放中打断为 cancelled；后续短句继续发声，无额外超时取消。
真实模型/Gateway/Vidu/ARTC 未替换，本轮仍未使用真实麦克风输入。

另修复 UI 状态：本轮音频确认超时走可恢复中文提示，不再在 controller 已回到 idle 后
强行设置连接 error；新一轮 rendering 时清除旧提示。回归覆盖未确认内容不放音、无假 started/ended、
原会话重试和持续人物视频。最终示例测试 145 项通过；浏览器回归另覆盖持续连接和恢复流程。
本地记录位于任务 `.checks/start-recovery/`。

## 起播前无声张嘴的回归（2026-10-23）

对比原版 `7856f32`：24 kHz PCM 原样上传；当前版保留内容和包边界，但需通过
500 ms 安静边界才释放缓存，因此初始发送时序不同。新增上传测试覆盖缓存前后
每包逐字节相等、重复 turn.ready 不重发、audio.end 不补零。原版另发送最终回复
文本 type 10，当前适配器未上传该文本；本次未改变这一点。

定位到本地画面逻辑错误：起播内容确认前展示实时视频，放音后切换历史帧，导致画面
倒退、同一口型先无声出现再随声音出现。现改为确认前保持最后待机帧；确认后使用
设备输出时钟映射视频，呈现时间单调递增。远端采集不断流，待机时仍连续显示。

修复后执行一轮真实模型/Vidu/ARTC 回复，获得正常 playback.started 和 playback.ended。
实际 canvas 绘制 282 次，其中确认期间 57 次均保持同一捕获时刻；整段绘制无时间回退。
这验证了本地重复呈现已消除，不等于对供应商生成的所有口型或逐音节偏移完成验收。
测试录像及实际绘制时间记录保留于任务 `.checks/mouth-sync/`。

## 当前会话级持续连接验证（2026-10-23）

恢复会话级持续连接后，两组三轮真实对话均使用同一个 Vidu live 和同一 RTC 订阅，
未在轮间 hangup；仅最终“结束”时挂断。第二组包含远端音频缓冲对应的视频延迟调整。
标准 Gateway、真实 Qwen Audio 3.0 Realtime Plus / longanqian、真实 Vidu/ARTC SDK 7.1.9；
仍通过文字触发模型语音，本轮未用真实麦克风发言（无头测试拒绝麦克风权限）。

- 两组第一、第三轮均实际起播，以 content_matched / playback.ended 结束。
- 两组第二轮播放中打断，立即停止并清除本地远端音频节点；发送 playback.cancelled。
- 第二组本地音频增益归零及断开比取消回执早约 0.2 ms。
- 第二组打断后 150 ms 到下一轮开放声音前，230 次输出 RMS 采样均为 0；
  同期视频解码帧从 362 增至 507，证明静音期间视频连接持续工作。
- 每轮均经安静边界、内容确认后起播；RTC 成功、视频帧和 audio.done 均未伪造回执。
- 新增回归覆盖：同一 live 多轮复用、取消后旧缓冲不下发、新输入等待 turn.ready、
  重复旧句在隔离期被丢弃、安静边界后的不同旧内容不放音、输出时钟、未匹配上限、结束清理。
- 诊断阶段另有一轮未找到高相关起播锚点，按上限取消且未播放；不能声称任意网络/编码条件下均能匹配。
- 音频缓冲与视频帧缓冲使用相同时间偏移，已经实际显示并录制人物画面；精确逐音节口型偏移仍未人工标注测量。
- 持续 RTC 没有逐回复媒体 ID 或 interrupt 排空确认。供应商若在安静边界后重放与新回复
  完全相同的波形，PCM 无法判断来源；内容对齐不是供应商侧绝对排空证明。
- 待机持续视频也可能计费。默认会话上限 30 分钟，不能以麦克风静音代替结束。

本地测试录像与结构化记录保留在任务的 `.checks/session-dialogue/`，未将密钥或 RTC Token 写入仓库。

## 历史：按回复创建 live 的验证

2026-10-23，本地基于 `5d0b9e1` 加本次尚未提交的播放器/内容对齐修改，执行了两组
三轮真实服务测试。模型为用户现有 DashScope 接入的 Qwen Audio 3.0 Realtime Plus，
音色 longanqian；Vidu 默认参考图片，ARTC 官方 Web SDK 7.1.9，Chrome 无头浏览器。
Gateway 使用本仓库标准 CLI、backend none、独立本地配置/数据目录，与现有服务隔离。

测试经统一页面提交文字，真实模型生成语音，再由真实 Vidu/ARTC 返回数字人音视频。
没有替换 Gateway、模型、Vidu 或 RTC SDK，也没有伪造播放回调。浏览器观察钩子仅记录
GCP 事件、实际 WebAudio 输出、静音门控和视频帧；录制使用浏览器 MediaRecorder。
SDK 文件使用本地缓存的官方固定版本，媒体传输仍连接真实 ARTC。

## 场景与结果

| 场景 | 两组测试结果 |
| --- | --- |
| 短句“你好，这是数字人真实对话测试。” | 均实际起播并发送 playback.ended |
| 长回复介绍春夏秋冬，起播后约一秒点击打断 | 均发送 playback.cancelled；未把取消当成自然播完 |
| 紧接着说“上一轮已停止，现在是新一轮。” | 均正常起播和结束，无旧回复回执串入 |
| 会话关闭 | 每组 3 个 live 均发出 interrupt/hangup 并关闭控制连接；测试 Gateway 和浏览器关闭 |

第一组：首句走 content_estimated；第三轮走 content_matched。
第二组：首句走 playback_delay_limit；第三轮走 content_matched。
因此本次验证不声称所有自然结束均由精确匹配证明；估算和主动关闭上限确实被使用。

第二组的可核对指标：

- 长回复取消回执前约 0.4 ms，本地可听增益已归零并断开。
- 取消后留出 150 ms 的观测余量，到下一轮音轨接入前，主播放通路 127 次采样 RMS 均为 0。
- 收到真实视频轨道，解码宽度 864；有声时出现可见人物视频和口型变化。
- 第二组浏览器未记录 Gateway error、renderer.error 或媒体 play 错误。
- 第二组首轮视频首帧比主输出首次非零能量晚约 360 ms；后两轮视频首帧先于音频约 240～250 ms。
  这是首帧/首次能量的就绪差，不是逐音节口型偏移测量；首轮仍存在可感知的画面启动延迟。
- 完整音视频和结构化事件记录留在本地测试产物中，没有将密钥、RTC Token 或完整厂商响应写入仓库。

这些证据验证了输出门控、旧音频隔离、回执关联与下一轮恢复；RMS 观察点位于实际
播放图，不能证明用户物理扬声器状态。精确口型同步仍需结合录制音视频人工复核，
本次没有获得厂商提供的逐回复自然媒体结束标记或音画偏移测量。

## 实测发现并修复

1. 测试最初使用 Cherry 音色，现有模型端点拒绝并返回支持列表；测试改用 longanqian。
   这属于本次模型接入配置，不更改用户持久配置或默认产品音色。
2. 原播放器调用 setRemoteViewConfig 后立即 play，与 SDK 的异步视频加载竞争。
   真实浏览器返回 AbortError（play 被新 load 打断），随后整轮被误报为 autoplay blocked。
   现直接使用公开 getVideoTrack({ userId, streamType: 0 })，由播放器一次性绑定视频并播放，
   与音轨一样自行控制取消与清理。修复后两组三轮真实测试通过。
3. 增加视频只绑定/播放一次、取消后迟到视频轨不能复活的回归测试；自动播放真实失败时仍取消，
   不吞掉错误或伪造播完。

## 限制

- 本次是文字触发的真实有声对话，未使用用户麦克风验证 ASR 或声学打断。
- 长回复在起播后打断，验证的是打断路径，不能作为完整长句播完或长时间稳定性验收。
- 真实弱网、长时间运行、多设备及逐音节音画偏移尚未验收。
- estimated 与 delay-limit 仍是客户端估算/主动关闭契约，存在迟到媒体被截断的可能，
  需要维护者确认，PR 保持实验状态。
- 服务均为人工触发，有收费会话资源上限；CI 仅运行离线/模拟测试。
