# 消息流分析

一次会话在前台、协调层、后台之间传了什么，按时间顺序展开，用来分析行为、定位问题、
找出可以改进的地方。

默认关闭。

## 开启

```dotenv
QWEN_AUDIO_AGENT_FLOW_TRACE=on
```

重启 Gateway 后访问 `http://<地址>/?analysis=flow`。

默认关闭是刻意的：链路里含用户说过的话、发给后台的 prompt、后台的推理与回答，不应当
因为将来可能要看而一直收集。默认只记内存，不落盘，重启即清空。

### 让记录活过重启

只记内存意味着重启会抹掉「正要去看的那一次」。想保留就再开一个开关：

```dotenv
QWEN_AUDIO_AGENT_FLOW_TRACE_FILE=on
# 保留天数，默认 7
QWEN_AUDIO_AGENT_FLOW_TRACE_DAYS=7
```

事件按 JSON Lines 追加到配置目录下的 `flow/flow-<日期>.jsonl`，文件权限 `0600`，
每天一个文件，超出保留天数的自动清理，单日文件有大小上限。启动时读回最近的记录，
读回量不超过内存本来的上限。

**这是第二个独立开关，不是跟着分析一起开的。** 只记内存、重启即清是默认的一条隐私
性质；落盘意味着用户说过的话与模型的回答会留在磁盘上，这个决定应当单独做。

写入是批量的，不在每个事件的路径上落一次盘；写失败只记一条告警，不会影响正在进行的
交互。

## 一次交互能看到什么

以「看看我桌面上有几张图片」为例：

```
前台     用户开始这一轮      前台模型
前台     用户说             看看我桌面上有几张图片
前台     前台调用工具        委派给后台，附它整理出的目标
协调层   任务已接受 / 开始执行
后台     协调轮次开始        后台模型、后端名、会话是新建还是续接
后台     向后台发起调用       模型、用户原话、完整 prompt
后台     后台请求授权        工作区外的路径
协调层   授权已答复
后台     后台模型推理        它打算怎么做
后台     后台执行工具        发起者、执行者、工具、目标、返回内容
后台     后台模型推理        它从返回里得出什么
后台     后台给出回答        回复内容
前台     前台回复用户        用户实际听到的话
```

这个顺序是刻意的：**模型的话排在它引起的动作之前**，读下来就是「打算做什么 → 做了
什么 → 看到什么 → 得出什么结论」。超过两秒的间隔会单独标出，因为延迟通常藏在等待里。

## 谁决定、谁执行

一次交互涉及多个模型和多个执行方，页面把它们分开标注，混在一起就无法归因：

| 事情 | 由谁负责 |
| --- | --- |
| 要不要委派给后台 | 前台 Realtime 模型 |
| 有哪些工具可用 | Gateway（注入 MCP 工具） |
| 调哪个工具、传什么参数 | 后台模型 |
| 实际执行工具 | 后端 Agent 进程；Gateway 注入的那几个由 Gateway 执行 |
| 看图 | 后台模型自己，或配置的独立视觉模型 |

所以工具事件上有两个字段：**发起者**是做决定的模型，**执行者**是真正跑这段代码的
进程。它们经常不是同一方。

## 能用它分析出什么

这些都是从真实链路里读出来、而不是从日志里猜出来的：

**答案是查出来的，还是记忆里的。** 后台会话跨进程持久，模型可能直接用旧记忆回答。
链路里「零工具调用却给出了具体答案」就是这种情况——回答可能仍然正确，但已经过期而
无人知晓。

**工具调用是否在反复失败后才成功。** 参数格式不对时模型会重试，从外部只看到最终的
「已完成」。链路里能看到失败次数与每次的错误内容，那是提示词或参数约定该改进的信号。

**时间花在哪。** 每一步的相对时间加上长等待标注，能区分「模型在想」「后端在跑工具」
「在等授权」，而不是笼统的一句慢。

**前台说的和后台算的是否一致。** 两端的原话都记着。后台结果正确而前台表述走样，是
只看任一侧都发现不了的一类问题。

**该问的授权有没有真的问。** 授权请求、答复、以及它归属于哪一轮都在链路上，能看出
是自动放行了还是走了用户确认。

## 自动标注的可疑之处

除了让人读，页面也会主动指出下面这些：

| 规则 | 含义 |
| --- | --- |
| `permission-after-terminal` | 授权请求归属到已结束的任务。前台不会为已结束的任务弹出授权，后端因此一直等待，最终表现为模型声称没有权限 |
| `permission-unanswered` | 授权请求迟迟没有答复 |
| `task-idle` | 任务进入运行后长时间没有任何后台活动，请求可能没真正离开协调层 |
| `request-without-response` | 后台调用发出后没有返回 |
| `unknown-session` | 事件指向协调层不认识的会话。会话跨交互存在，因此这条规则需要外部提供已知会话集合，否则保持沉默 |

规则刻意保守。一个总在误报的工具会被忽略，那时它比没有更糟。

## 页面

**会话列表**：每个会话一行，标出轮数、事件数、最近一句请求，以及是否有失败或可疑之
处。打开页面时自动选中最近的会话。

**可疑之处**：命中的规则与解释，点标题跳到对应事件。

**经过**：整个会话的时间线，轮次之间有分隔，可按层筛选。

**详情**：点某一行，右侧展开该事件的全部内容，被选中的行会高亮。短字段是键值表，
prompt 与回答这类长文本单独成块、可独立滚动。

## 分析真实行为时的一个前提

后台 Agent 的会话是**跨进程持久**的：重启 Gateway 只清空链路记录，后台模型仍然记得
之前所有对话。

要观察它真实的执行行为，需要同时清掉持久化的会话映射（用户配置目录下
`state/acp-sessions.json` 里对应后端的条目）。否则会看到「零工具调用却答对了」这种
令人困惑的链路——那不是记录漏了，是它确实没做，只是复用了记忆。

## 记录的取舍

- **心跳不记**。任务进度事件每秒一次，只说明「还活着」。记录它会让一条链路装满相同
  内容，把解释问题的事件挤出去；时长本来就能从起止时间戳算出来
- **流式输出按段落记**，不逐 token 记。模型的文字在工具调用前和回答前各汇总一次，
  既不会淹没时间线，又保住了因果顺序
- **一次工具调用一行**。ACP 用两条消息描述同一次调用，且完成消息里的标题常常是文件
  路径，所以按调用 id 合并：名字取自宣告，目标与返回取自完成
- **失败也记**。包括工具失败与视觉模型调用失败——分析恰恰发生在失败时，只记成功等于
  最需要的时候没有记录
- **图像不记内容**，只记数量。几 MB 的 base64 对读者没有意义

文本字段复用日志的脱敏规则，密钥类字段不会留下。prompt、回答、工具返回这类载荷字段
的长度上限明显更大，因为它们正是要读的东西；其余字段保持较小上限。

## 为什么按会话而不是按轮次

存储按轮次，读取时合并成一条时间线。

值得找的故障多是会话级的：某一轮的授权请求被归属到另一轮、某个监听比安装它的轮次
活得更久。按轮次分开看，因和果会落在两个页面上，工具对它最该发现的问题恰好是瞎的。
规则判定也跑在合并后的事件流上，正是为此。

按轮次存储则保证长会话不会把单条链路的事件上限撑爆。

一次交互一个 `flowId`，由已有的 `turnId` 派生，与日志字段天然对齐，不引入第二套标
识。后台用协调轮次 id 认识同一次交互，两者在每个任务事件上同时出现，所以映射是被
学会的，已经落在另一个名下的事件会被合并过来。

## 接口

页面用的就是这些，也可以直接取用：

```
GET /api/sessions/flows            会话列表，含轮数与可疑计数
GET /api/sessions/:id/flow         一个会话的完整时间线与判定结果
GET /api/flows                     按轮次的链路列表
GET /api/flows/:flowId             单轮的事件与判定结果
GET /api/flows/:flowId/stream      SSE，先发快照再实时追加
```

关闭时一律返回 404。

## 实现

| 文件 | 作用 |
| --- | --- |
| `server/src/observability/flow-recorder.mjs` | 收集、聚合、脱敏，环形缓冲有上限 |
| `server/src/observability/flow-anomalies.mjs` | 规则判定，纯函数 |
| `server/src/observability/flow-store.mjs` | 可选落盘、读回与过期清理 |
| `server/src/observability/flow-trace.mjs` | 两个开关与单例装配 |
| `web/src/flow-timeline.js` | 事件到可读行的转换 |
| `web/src/FlowAnalysis.jsx` | 页面 |

- **任务层零改动**。`TaskManager` 已有 `subscribe()`，记录器作为一个普通监听者接入，
  状态机与事件发射一行未改
- **关闭时是空实现**。所有埋点无条件调用 `flowRecorder`，关闭时它是一个什么都不做的
  对象，因此调用处没有分支，行为与未接入前完全一致
- **有上限**。默认保留最近 50 条链路、每条至多 500 个事件。一个会无限增长的观测工
  具，比它能帮忙找到的问题更糟
- **observability 是叶子层**。依赖约束测试限定它只能依赖配置与共享日志，这样记录始
  终是旁观者，不会反过来被业务层依赖
