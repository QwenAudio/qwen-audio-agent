# PR 说明草稿：Vidu 作为独立延迟展示

本例接入 Vidu S2 Avatar / ARTC，并保留桌面浮窗、原悬浮球选项、默认及自选角色图片、演示视频。
框架仍使用标准 Gateway 与原有模型、prompt 和工具配置，Vidu 只展示源音频的延迟音视频版本。

## 为什么采用展示旁路

将 Vidu 实际播放进度加入 Gateway 播报决策，会把供应商处理、网络和媒体缓冲延迟引入原始
Agent 的回执与后续播报时序。即使精确测得返回进度，也不会自动修正模型已有的对话上下文。

例如源回复第 5 秒说“先关闭旧服务”，第 8 秒说“再启动新服务”。若数字人延迟 3 秒，
用户在本地第 8 秒说“等等”，可能是在回应刚听到的“关闭旧服务”；模型上下文却可能已经
包含“启动新服务”甚至更多内容。若同时因原始 API 的打断事件硬切数字人，还会造成口型、
动作或句子突然中止。仅更换播放回执的时间线无法保证模型理解了用户实际听到哪个位置。

本方案保留原始音频作为唯一的 Agent 播放时间线，将它静音并把副本交给 Vidu。原始的
语音检测、打断、正常结束和任务播报调度不等待数字人；已经上传的内容允许连续展示。
这样避免展示进度与源时间线混用导致额外的 Agent 行为变化，并避免逐轮远端硬打断。
**它不能消除用户实际听到位置与模型认知的差异**：数字人可能继续播放已取消内容，且存在
延迟。要解决精确的语义打断，需要另行实现模型所支持的已听位置反馈及上下文截断。

## 实现与验证边界

- 原始真实 PCM 经过本地 Web Audio 调度；默认 GainNode=0。回执明确对应源时间线。
- 原声对照只切换音量及画面可见性，两种模式共用同一播放器、PCM 和回执路径。
- ARTC 同一原生媒体元素播放原始音轨和视频轨，不重排音视频、不增加播放门槛。
- 不使用对齐、结束估算、正常收尾 interrupt 或 Vidu 回调来改变 Gateway 状态。
- Vidu 初始化或故障不阻塞 Gateway；长期凭证保留服务端，资源和排队有界。
- 与原审核中实际 ARTC 播放回执、立即远端取消和旧媒体隔离的要求存在明确差异，需讨论确认。

不作为新方案的真实服务验收证明。PR 继续保持实验状态。
