# Quick-query lane RFC

状态：提案

本文定义 Realtime 前台与已配置后台 Agent 之间的一条小型只读通道。它用于
需要后台当前知识或状态、但不值得创建用户可见 Work 的问题。

## 目标

- 对一个有边界的只读问题直接回答，不把 Work 追加到 owner FIFO 队列末尾。
- 复用 owner 的持久协调 Session，确保答案仍来自用户配置的后台及其只读能力。
- 保持前台对话连贯：先立即承接查询，验证结果到达后再经既有 Agent Delivery
  路径自然回答。
- 快速路径设置 15 秒硬上限。超时后取消查询，并将同一问题提升为普通 Work。

## 非目标与安全边界

- 文件写入、代码修改、设备操作、购买、权限请求和多步编排不属于此通道，继续
  使用 `spawn_thinking`。
- 前台模型只按用户意图选择通道，不能选择后台 Session、执行策略或工具。
- 快速查询不创建用户可见 Task ID。提升后的 Work 获得普通 Task ID，并复用既有
  通知、取消与持久化路径。

## 生命周期

```text
quick_lookup(question)
       |
       +--> 立即回执 --> 前台简短承接
       |
       +--> 协调 Session，优先级 10
                 |
                 +--> 15 秒内回答 --> Agent Delivery 回复
                 |
                 +--> 超时 ----------> 取消 + 创建普通 Work
                                        + Task 播报
```

通道只在等待协调 Session 时体现优先级。已经运行的后台回合不会被强行打断；
它释放 Session 后，快速查询排在普通等待回合之前。用户开始新回合或明确打断时，
查询失效，晚到的结果直接丢弃。

## 结果契约

Adapter 返回普通后台文本和可选内容块。Gateway 负责用户可见封装，并要求 Realtime
前台只能依据该结果回答。查询失败时不能猜测答案。

超时提升保留原始规范化问题和当前 owner 上下文，因此普通 Work 可以在快速路径
超时后继续完成，且不会重复提交请求。

## 交付与可观测性

立即回执与当前语音回合关联。最终答案使用 `origin=quick-query` 和同一回合关联，
等待安全的全双工插入窗口；回合代次不再当前时丢弃。Adapter 可以记录耗时和结果
诊断，但不能把问题正文或 Provider 内部 ID 持久化到公开 Task 表面。

## PR 拆分

1. 本 RFC：语义、边界、生命周期、超时、提升和交付方式。
2. 实现：`quick_lookup`、协调器优先级调度、超时提升、取消与一致性测试。
3. 摄像头后续：一次性拍照提问、相机状态反馈和隐私文案；与 quick-query 独立。
