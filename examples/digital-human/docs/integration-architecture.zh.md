# Vidu：双连接客户端与原生媒体适配

[返回总览](../README_ZH.md) · [Vidu 配置](vidu.zh.md) · [音频流程](audio-processing-flow.zh.md)

沿用双连接架构和公开 Client SDK；数字人实现全部位于本示例，不修改 Gateway、模型 Provider、prompt、工具注册或 GCP。DHAV 的公共播放控制器和真实播放回执保持不变。

## 连接与职责

- `useDualConnection` 负责普通 Gateway 连接、输入和事件分发；按适配器能力决定是否声明播放回执。
- Vidu 客户端适配器转交助手 PCM，并隔离取消的回复和旧 epoch。
- 示例服务端持有厂商长期密钥，创建/挂断 live，签发临时 RTC 凭证。
- ARTC 播放器让同一原生媒体元素播放供应商音视频，不拆解重排媒体。
- 已删除静音源播放器与原声对照模式；Vidu 不协商或发送播放回执，不以源音频时长估算完成。

## 打断与故障

用户打断后，本地先静音、暂停并解绑旧媒体；服务端再尽力 interrupt 和 hangup。下一条有效回复才分配新 epoch、live 与 RTC channel，避免迟到媒体复用旧流进入新回复。正常输入结束不等于媒体结束，不据此挂断。

故障明确报错、停麦并要求重连，不自动从头播放原始音频。重建 live 会增加延迟并可能增加费用；不应把这种隔离方式描述为零成本的无缝切换。

## 尚未完成的交付能力

当前公开供应商接口缺少逐回复媒体结束及旧媒体已排空的确认，依据见 [Vidu 指南](vidu.zh.md#回执边界)。不发送错误回执只是修复边界，不是实现可靠任务播报；正式合并仍需补齐供应商能力和真实部署验证。
