# Vidu：双连接客户端与原生媒体适配

[返回总览](../README_ZH.md) · [Vidu 配置](vidu.zh.md) · [音频流程](audio-processing-flow.zh.md)

沿用双连接架构和公开 Client SDK；数字人实现全部位于本示例。Gateway 只新增显式协商无播放回执时的通用降级，不包含供应商实现、新公开协议或厂商 SDK 依赖。DHAV 的公共播放控制器和真实播放回执保持不变。

## 连接与职责

- `useDualConnection` 负责普通 Gateway 连接、输入和事件分发；按适配器能力决定是否声明播放回执。
- Vidu 客户端适配器转交助手 PCM，并隔离取消的回复和旧 epoch。
- 示例服务端持有厂商长期密钥，创建/挂断 live，签发临时 RTC 凭证。
- ARTC 播放器让同一原生媒体元素播放供应商音视频，不拆解重排媒体。
- 已删除静音源播放器与原声对照模式；Vidu 不协商或发送播放回执，不以源音频时长估算完成。
- `onInputReady` 在 RTC 入会且接收配置完成后放行源 PCM，不等待返回媒体；`onReady` 仅表示媒体可播放，避免首包循环等待。
- 配套 Gateway 展示生成字幕、保留普通对话，并按生成完成释放调度；不伪造播放完成，自动后台结果通知保持 pending，框架任务记录和查询/控制接口保留。本例没有完整任务管理 UI。

## 打断与故障

用户打断后，本地先静音、暂停并解绑旧媒体；服务端再尽力 interrupt 和 hangup。下一条有效回复才分配新 epoch、live 与 RTC channel，避免迟到媒体复用旧流进入新回复。正常输入结束不等于媒体结束，不据此挂断。

故障明确报错、停麦并要求重连，不自动从头播放原始音频。重建 live 会增加延迟并可能增加费用；不应把这种隔离方式描述为零成本的无缝切换。

## 使用限制与部署要求

当前公开供应商接口缺少逐回复媒体结束及旧媒体已排空的确认，依据见 [Vidu 指南](vidu.zh.md#回执边界)。Vidu 是默认关闭的可选商业接入示例，不适合依赖自动播报确认的生产流程。传统客户端行为保持不变。

需要包含通用无回执降级的 Gateway，对应版本发布前使用本分支源码；旧已发布版本不能据此宣称兼容。本版尚未完成真实 Vidu 验收，历史视频和采样也不作为当前证据；当前验证状态见 [验证记录](presentation-validation.zh.md)。
