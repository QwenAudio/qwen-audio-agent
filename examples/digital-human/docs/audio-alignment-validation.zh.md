# Vidu 音频内容对齐实测

2026-10-23，在本机使用现有账户、默认参考图片、真实 Vidu 组件 API 和官方 ARTC
Web SDK 7.1.9 先进行了 4 次短会话采样，加入估算兜底后又进行了 1 次在线复测。
使用本地测试语音，不采集麦克风；结束后
关闭控制连接并释放 RTC。音频与诊断数据保留本地，不把凭据或付费服务响应写入仓库。

## 输入与发现

输入为 PCM16LE / 24 kHz / 单声道，总长 11.74 秒，包括五段短句、句间停顿，
其中同一句分别在第二段和最后一段出现。第四次另加 1 秒前置静音。
浏览器采集到的实际远端音轨为 48 kHz。

首次采样中，首句相关峰约 0.95，中段约 0.98，重复尾句的两个相关峰约为
0.9817 和 0.9815。仅搜索尾句无法区分它们。实际偏移从约 2.0085 秒逐步变至
2.1895 秒，证明单次延迟测量加源时长不可靠；必须持续匹配位置。

采用 2 kHz 低通降采样、归一化互相关、顺序窗口跟踪后：

| 验证 | 结果 |
| --- | --- |
| 真实采样 1 的离线顺序匹配 | 推进至末尾，候选结束位于远端采集起点之后约 13.599 秒 |
| 真实采样 2 的离线顺序匹配 | 推进至末尾，候选结束约 13.330 秒 |
| 真实采样 3、4 | 部分窗口无法可靠连续匹配，拒绝完成；不跳过失配内容 |
| 用采样 1 的真实回传文件在 Chrome 媒体图重放 | AudioWorklet 连续匹配到末尾，设备输出时钟通过候选位置后触发 onDrained |

浏览器重放使用本地 RTC SDK 替身传入已录制的真实音频；这一步验证实际浏览器播放图、
输出时间戳和完成回调，不声称是真实网络会话成功自然结束。4 次真实会话未获得稳定的
在线完成结果，因此保持默认关闭与实验状态，不能把两次离线成功作为完整商业验收。

## 严格匹配阶段的算法与边界

见 [Vidu 指南](vidu.zh.md)。大窗口跨越重采样或抖动变化时，回退到四个 100 ms
片段逐一验证，不能靠降低到任意相似度或直接跳段继续。完成要求输入已封口、顺序
检查点推进至末尾、尾部高相关、观察到尾后安静区间及设备输出时钟通过；然后主动
关闭该轮媒体。这是已知输入内容的播放确认，不是厂商自然媒体结束通知。

误差、音频损失、过短语音、时间伸缩可能导致正确语音也无法完成。仍需更多真实服务
样本及维护者对内容对齐回执契约的确认。没有恢复静音回复时钟、源音频回放或固定
延时完成。基础方法参考 [归一化前的互相关与 lag 定义](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.correlation_lags.html)
及 [浏览器输出时间戳](https://developer.mozilla.org/en-US/docs/Web/API/AudioContext/getOutputTimestamp)。

## 新增估算兜底后的验证

前述结果记录的是严格匹配版本。加入估算兜底后，重新逐块回放同一批录音，未重新调用收费接口：

| 采样 | 当前结果（相对于各自远端采集起点） |
| --- | --- |
| 1 | aligned，13.599 秒 |
| 2 | aligned，13.330 秒 |
| 3 | estimated，14.080 秒；最后可靠锚点：源 10.600 秒对应回传 12.622 秒 |
| 4 | estimated，15.0185 秒；最后可靠锚点：源 5.000 秒对应回传 6.996 秒 |

估算使用最后可靠锚点加剩余完整源时长，保留最大已知延迟并额外增加 250 ms。
必须输入已封口、采样位置超过预计结束、最近 120 ms 安静，并等待设备输出时钟。
持续声音会延后结束；等待期间出现新声音会撤回候选。没有足够可靠锚点仍不估算。

采样 3 的真实回传文件在 Chrome 中重放，estimated 完成回调通过，回调元数据保留
锚点和预计结束时间。随后新增一次真实 Vidu/ARTC 在线复测，11.74 秒同一源音频
未加前置静音，得到 estimated：最后可靠锚点为源 10.800 秒对应回传 12.728 秒，
预计结束 13.918 秒，最终候选 13.9945 秒；设备输出时钟通过后触发 onDrained，
本地图关闭并释放真实会话。这些时间均为远端采集起点之后的相对时间。

仅一次在线通过，尚不能代表长句、多轮或弱网完成验收。估算不等于完整内容匹配，
尚未观测到的长停顿或新增延迟可能造成提前关闭；维持默认关闭和实验状态。

## 短音频补充

输入封口后，有声跨度为 80～800 ms 的回复采用整段匹配，阈值沿用可靠匹配的 0.8，
无需三个检查点；仍需末尾安静及设备输出时钟。单元测试覆盖 80、100、200、400、
600、799 ms，以及输入未封口、截断、无关音频、首尾长静音和回传后才封口的情况。

另从采样 1 提取源音频开头的 720 ms 短句和对应真实远端片段：离线相关性约 0.962，
Chrome 实际媒体图重放后约 0.836，通过 short 路径和设备输出时钟完成回调。
这一步复用已有录音，不是新增独立短回复的收费服务验收。

## 最大延迟上限

新增最后一道主动关闭策略：从播放器开始处理本轮 RTC 会话时用单调时钟计时，
输入封口后以完整源 PCM 时长加默认 5 秒作为上限。它不依赖匹配、静音、后续回传
采样或设备输出时间戳。已实际起播则按 estimated / delay-limit 结束并关闭本地媒体；
没有起播则失败取消，释放队列。

本地 Chrome 以持续无关声音模拟始终无法匹配的输出，源参考音频为 0.72 秒，
在约 5.7323 秒触发 delay-limit 回调，符合 5.72 秒上限加轮询间隔。
该测试不调用收费服务。单元测试还覆盖临界值、输入未封口、完整源时长包含静音、
无采样、无设备时间戳、无起播与旧回复的截止回调隔离；全部 142 项回归通过。
这道上限是主动关闭约定，不是完整播放证明，可能截断超过允许延迟的语音。


## 会话级 RTC 的起播隔离

恢复会话级连接后，内容匹配也用于开放声音：每轮先观察 500 ms 新鲜的远端安静，
服务端才释放新参考 PCM；浏览器保存实际远端采样，匹配到当前参考的高相关锚点后才调度播放。
模型 PCM 仍只用于比较，不会被当作声音播放。静音监听节点不参与 started/ended 回执。
完整匹配/估算的远端采样位置必须通过实际调度偏移映射到设备输出时钟；不再使用采集时钟作为播放时钟。
短句也需通过高相关内容确认，过短或无法确认时在上限内取消，不能将未起播标成结束。
打断同步清除已调度的远端采样，持续视频不关闭；更完整的当前实测见真实对话验证文档。
