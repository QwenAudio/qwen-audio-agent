# 六段演示：录制与验收

自动测试验证协议、执行和状态流转；真实语音录制验证模型理解、工具选择和播报体验。离线测试通过不等于语音演示已经实测成功。

## 准备

按[示例说明](../README_ZH.md#快速开始)启动四个进程，浏览器取消静音并确认连接。地图和路线需要高德配置；新闻沿用框架的[联网搜索配置](../../../docs/guides/web-search.zh.md)。正式录制前验证搜索和原文读取，不依赖免 Key 搜索兜底的可用性。

调试面板检查真实工具和结果，左侧对话区保持纯语音。每段开始前确认车况、导航偏好、已存技能和记忆，避免上一次录制影响本次。

## 1. 一句话，多个独立意图

> 把后排车窗打开，空调调到二十二度，大灯打开，音乐音量调到六。

预期四个前台 MCP 调用：`vehicle_window_control`、`vehicle_temperature_control`、`vehicle_light_control`、`music_volume_control`。检查它们是否由同一模型响应产生。各项分别执行、回填结果，全部完成或明确失败后，框架只请求一次总结。

验收：四项实际状态正确，最终回复覆盖全部结果；一项失败不应掩盖其他结果。允许简短自然的执行前回应，但不能提前声称完成。框架不强制模型并行规划：模型若分多次响应调用，该次录制不能算作“一次响应输出多个调用”。

## 2. 多途经点导航

> 从这里出发，先去五常地铁站，再去城西银泰，然后去武林广场，接着去杭州东站，最后到萧山人民广场，按这个顺序直接开始导航。

预期前台 `navigation_start`：前四个地点为有序 `waypoints`，最后为 `destination`。检查工具参数顺序、真实路线及地图显示；不将多地点误判成后台任务，成功后不再询问是否开始。

前台 MCP 执行默认超时为 10 秒，连接与工具发现仍为 8 秒。高德驾车路线请求在 Service 进程内保持至少 600ms 的发起间隔，避免多段连续查询触发限流；首次请求不额外等待。超时须明确失败，不声称导航成功；地名歧义应追问。外部服务耗时也需正式录制时确认。

## 3. 点击屏幕，静默感知

先选其他路线偏好，再点击“不走高速”。保持安静，确认没有主动播报；然后问：

> 我们现在设置的是走高速，还是不走高速？

Service 确认状态后，客户端通过 GCP `cockpit.navigation.preference_changed` 同步上下文，模式为 `context`，不创建回复。助手可直接依据该状态回答。

验收：点击不是伪造用户文字消息，失败操作不更新偏好。语音改变偏好、刷新或重连后也以最新状态为准。这里知道的是路线偏好，不是车辆当前是否已驶上高速。

## 4. 后台整理新闻，前台继续聊天

> 帮我看看过去二十四小时 AI 领域有什么值得关注的新闻，挑三条，每条一两句话，带上来源，整理好了告诉我。不用做深度研究。

任务开始后立即继续与前台聊天，例如“今天工作有点累，陪我聊会儿吧”，或“顺便把空调调到二十三度”。预期 `spawn_thinking` 启动后台任务，座舱 Agent 搜索相关新闻、必要时用 `fetch_url` 核对来源；前台仍可对话和车控。完成后简要播报，带来源的文本作为 A2A artifact 返回。

验收：确有真实检索，来源和日期可追溯，前台不被后台阻塞。无需凑够多轮搜索或固定运行时长；找到足够信息就结束，消息不足三条时如实说明。读取失败或缺少来源须说明，不能用模型知识冒充当天新闻；仅有摘要时不声称已读原文或交叉核验。

这段只展示异步任务与前台对话并行，不演示完整 Deep Research。24 轮模型响应、32 次工具调用和 10 分钟是示例自身的保护上限，不是搜索服务额度，也不是必须用满的目标。达到次数预算是后台内部的正常收尾条件，停止检索并返回已有结果，不向前台透出预算或报告失败；内容缺少来源、未核验等事实仍如实说明。真正超时或取消仍按失败或取消处理。文本在任务 artifact/结果中，客户端尚无专门的报告阅读面板。

## 5. 语音创建技能，手动调温触发

先将主驾空调设为 20℃或以上，再说：

> 创建一个低温提醒技能。当我把空调调到十九度及以下，就提醒我：当前温度较低，请注意保暖。

预期前台 `custom_skill_create`，使用 `kind=event`、`trigger={type:"vehicle_temperature",field:"acTemp",max:19}` 和用户希望的 `reminder`。创建只保存，不调温，不立即播报提醒。可在“设置 → 技能”查看条件。

点击底部主驾温度减号，从 20℃降到 19℃。Service 观察变化，客户端通过 GCP `cockpit.skill.triggered` 请求自然提醒。

验收：20→19 提醒一次，19→18 不重复；升到 20 再降到 19 可再次触发。删除后不提醒，重建服务仍可加载。没有定时轮询模型或执行用户代码；这里只支持结构化温度区间，不是任意事件编程平台。

在语音连接可用时演示。客户端暂存短时未送达事件，超过 30 秒的提醒不补播；Service SSE 是实时流，不承诺跨断线持久补发。

## 6. 记住饮食偏好，推荐附近真实餐厅

> 我平时特别喜欢吃烧烤，不过不太能吃辣。

等本轮完成，在“设置 → 记忆”确认食物偏好和辣度要求都已保存。聊一句无关的话，例如“今天工作有点累”，然后问，刻意不重复菜系：

> 附近有什么适合我口味的餐厅？推荐两三家，先不用导航。

预期前台根据记忆搜索附近的烧烤店：`navigation_search_place({ query: "烧烤", nearby: true })`，或含义相当的简洁类别词。应返回并播报真实店名，结合实际地址、距离介绍两三家（不足时如实说明），而不是把“烧烤 不辣”当成一家店。辣度属于需要核实的要求；地图 POI 没有菜单依据时，应自然提醒点单时确认少辣或不放辣，不保证商家一定符合。

可选收尾：听完后说“就去刚才第一家，开始导航”。此时才把选中的真实店名作为目的地。想加强记忆演示，可以保持同一用户身份，在新的会话中只问上面的推荐问题，验证不是仅靠本轮对话历史。

沿用 `memory` 工具和 Markdown 记忆，没有“烧烤”关键词分支。附近餐厅推荐通过前台地点搜索完成；外卖下单才使用后台闪购。当前要求优先于过去偏好；“今天想吃”不应保存为长期偏好。地点搜索不修改导航状态；空结果不能用坐标解析伪造店名，接口异常也不能当作找到餐厅。

正式录制前先确认演示位置附近有相应店铺。也可将偏好改成日料、西餐等当地确实可搜索到的菜系，随后仍只问“附近适合我口味的餐厅”，不要预先编写店名或固定助手回复。

离线回归覆盖真实写入、重建 provider 后读取、用户隔离和删除；自然语音能否自动触发保存并用好记忆，仍由这段 live 录制验证。
